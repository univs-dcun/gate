# 온프레미스 최초 관리자 부트스트랩

온프레미스 납품에서 **최초 관리자 계정이 생기는 절차**를 적는다. DB 준비는
[onpremise-oracle-setup.md](onpremise-oracle-setup.md) 를 본다.

> **이 문서는 설치 절차다. 계약 문서가 아니다** (UG-323).
>
> 최초 관리자 부트스트랩은 **auth-service 기능이고 auth-service 는 `univs-dcun/msa-scaffold`
> 소유다.** 아래에 적힌 환경변수 이름·오류 코드·유효 시간은 **설명을 위한 것이고 단일 진실이
> 아니다.** 정확한 값은
> [`msa-scaffold docs/onpremise-contract.md`](https://github.com/univs-dcun/msa-scaffold/blob/dev/docs/onpremise-contract.md)
> **§5.4 「최초 관리자 생성 API」** 를 본다 (UMS-16). 그쪽이 바뀌면 이 문서는 모른다.
>
> 배포 구성(compose, `.env`, 설치 스크립트)은 `univs-dcun/onprem` 저장소를 본다.

관련 티켓: UG-320 / UG-323 / msa-scaffold UMS-3

---

## 1. 전제

온프레미스 인스턴스는 **고객사 한 곳 전용**이다. 조직이 하나뿐이므로 "누가 가입해서 조직을
만든다" 는 개념이 성립하지 않는다. 클라우드의 *가입* 에 대응하는 것이 이 절차다.

두 가지를 원칙으로 둔다.

**벤더(super admin) 상주 계정을 만들지 않는다.** 폐쇄망이라 우리가 원격으로 접근할 수도
없고, 은행·공공 고객은 벤더 상주 계정을 금지하는 경우가 많다. 지원이 필요하면 고객사
관리자가 만료일 있는 한시적 계정을 발급한다.

**설치가 끝난 시점에 우리는 고객 관리자 비밀번호를 모른다.** 아래 절차가 그것을 보장한다.
환경변수로 관리자 비밀번호를 시드하지 않는 이유도 같다 — 설정 파일·배포 이력·config 볼륨에
평문이 남고, 실무에서 기본값이 그대로 방치된다.

## 2. 절차

### ① 설치 토큰 생성

설치 담당자가 매 설치마다 새로 만들어 `.env` 에 넣는다.

```bash
openssl rand -hex 16
```

```
AUTH_BOOTSTRAP_INSTALL_TOKEN=<위 값>
AUTH_BOOTSTRAP_ADMIN_APP_ROLES=gate:ADMIN
```

**이 값이 없으면 관리자 초기화 API 가 통째로 막힌다(fail closed).** 설정을 빼먹었을 때
조용히 무방비가 되는 쪽이 훨씬 위험하다는 판단이다.

### ② 기동

```bash
docker compose -p gate up -d
```

auth-service 로그에 `Install token armed for 30 minutes` 가 찍히면 준비된 것이다.

**유효 창은 서비스 기동 시점부터 30분이다.** 놓쳤으면 auth-service 를 재시작하면 창이 다시
열린다 — 설치 중에는 재시작이 부담이 아니고, 이미 초기화된 뒤에는 창이 열려도 무해하다
(초기화는 1회만 성공한다).

### ③ 고객사 담당자가 직접 비밀번호를 입력한다 ★

**이 단계가 절차의 핵심이다.** 고객사 담당자를 불러 그 자리에서 입력하게 한다.

```
POST /api/v1/auth/admin/init
Content-Type: application/json

{
  "installToken": "<①에서 만든 값>",
  "email":        "<고객사 관리자 이메일>",
  "password":     "<고객사 담당자가 직접 입력>"
}
```

성공하면 한 트랜잭션으로 아래가 만들어진다.

| 만들어지는 것 | 내용 |
|---|---|
| 테넌트 | `AUTH_BOOTSTRAP_TENANT_CODE` (미설정 시 `default`) |
| 관리자 계정 | 입력한 이메일·비밀번호 |
| `auth:IAM-ADMIN` | 계정·권한 관리 권한. 이것이 없으면 아무도 계정을 만들 수 없다 |
| 제품 역할 | `AUTH_BOOTSTRAP_ADMIN_APP_ROLES` 에 적은 것 |
| 감사 이력 | `ADMIN_INITIALIZED` |

응답이 아래와 같으면 **토큰이 틀렸거나 창이 지난 것**이다.

| 코드 | 뜻 | 조치 |
|---|---|---|
| `AUTH-131` | 토큰 불일치 | `.env` 값과 요청 값을 대조 |
| `AUTH-132` | 30분 창 경과 | auth-service 재시작 후 다시 |
| `AUTH-133` | 토큰 미설정 | `.env` 에 `AUTH_BOOTSTRAP_INSTALL_TOKEN` 추가 후 재시작 |
| `AUTH-129` | 이미 초기화됨 | 정상. 이 인스턴스는 이미 관리자가 있다 |

> 토큰이 틀리면 이미 초기화됐는지 여부도 알려주지 않는다(`AUTH-131` 로 통일). 의도된 동작이다.

### ③' 고객사 담당자가 부재한 경우

엔지니어가 임시 비밀번호로 계정을 만들고, 고객이 **첫 로그인 시 반드시 변경**하게 한다.
그 순간 우리가 아는 비밀번호는 무효가 되므로 최종 상태는 ③ 과 같다.

### ④ 관리자 2번째 계정 등록

**폐쇄망에는 메일 비밀번호 재설정이 없다.** 관리자가 1명인데 그 관리자가 비밀번호를 잊으면
재발급해 줄 사람이 없어 시스템 전체가 잠긴다. 실제로 자주 터지는 사고다.

①~③ 이 끝나면 관리 화면에서 **두 번째 관리자 계정을 반드시 등록한다.**

### ⑤ 인수인계 확인

확인서에 아래를 명시한다.

- 관리자 계정 이메일
- **벤더는 관리자 자격증명을 보유하지 않음**
- 관리자 2명 등록 완료
- 지원이 필요할 때는 고객사 관리자가 만료일 있는 계정을 발급한다

## 3. 설치 체크리스트

```
[ ] 오라클 계정 5개 생성 (onpremise-oracle-setup.md)
[ ] 이미지 사내 레지스트리 반입, 버전 값을 반입 태그와 일치 (목록은 onprem)
[ ] gate-config 클론 + config-server 를 native 프로파일로 (경로·변수는 onprem 설치 절차)
[ ] JWT_SECRET 생성 (openssl rand -base64 48)
[ ] AUTH_BOOTSTRAP_INSTALL_TOKEN 생성 (openssl rand -hex 16)
[ ] 내부 NTP 설정 확인 — 시계가 어긋나면 토큰 만료·JWT exp 검증이 깨진다
[ ] 기동 후 30분 내 ③ 수행 (고객사 담당자 동석)
[ ] 관리자 2번째 계정 등록
[ ] 인수인계 확인서 서명
```

## 4. 복구 (break-glass)

관리자 전원이 접근을 잃은 경우. **서버 셸 접근이 필요하고, 수행하면 감사 이력에 남는다.**

1. `accounts` 테이블에서 대상 계정을 확인한다
2. 비밀번호 해시를 알려진 BCrypt 해시로 교체하고 `must_set_password` 를 참으로 둔다
   (첫 로그인 시 강제 변경되므로 임시 값이 남지 않는다)
3. 필요하면 `role_assignments` 에 `auth:IAM-ADMIN` 을 직접 넣는다

이 절차를 아는 사람을 제한하고, 수행 사실을 고객사에 알린다. **④ 를 지켰다면 이 절차가
필요할 일이 없다.**
