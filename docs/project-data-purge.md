# 삭제된 프로젝트의 생체 데이터 정리 (UG-303)

## 왜 필요한가

`DeleteProjectUseCase` 는 프로젝트 행에 `is_deleted = true` 를 찍고 API 키를 비활성화하는
것까지만 한다. 그 프로젝트에 등록된 **얼굴·손바닥 특징점과 저장소에 올라간 원본 이미지는
손대지 않는다.** 조회 경로가 전부 막혀 접근은 안 되지만 데이터는 남는다.

- **개인정보** — "프로젝트를 지웠다" 는 사용자 입장에서 그 데이터가 없어졌다는 뜻으로 읽힌다.
  삭제 요청에 대한 응답으로 실제 삭제가 일어나지 않는 것은 설명이 필요한 상태다.
- **저장소** — 원본 이미지가 회수 경로 없이 영구히 쌓인다. 이미지는 MinIO 가 아니라
  `${file.root-path}` 아래 로컬 경로에 있다 (`FileUtil.delete`).
- **온프레미스** — 납품처의 "이 프로젝트 데이터를 지워 달라" 가 수작업이 된다.

## 지금 상태: 기능은 들어 있고, 꺼져 있다

`gate.privacy.project-purge.retention-days` 를 **주지 않으면 아무것도 하지 않는다.** 대상
조회조차 하지 않는다.

되돌릴 수 없는 개인정보 삭제의 보존 기간은 제품·법무가 정할 값이지 코드가 기본값으로 정할
값이 아니다. e-KYC 이력은 규제 대상일 수 있고, 그 답이 나오기 전에 기본값으로 지우기 시작하면
되돌릴 방법이 없다.

## 켜는 방법

`gate-config` 의 `gate-service.yml` 에 값을 준다. 재기동하면 적용된다.

```yaml
gate:
  privacy:
    project-purge:
      retention-days: 30
```

> ⚠️ **공용 `gate-service.yml` 에는 넣지 않는다.** onprem 저장소의 `config/spring` 은 gate-config 를
> **통째로 복사**한 사본이라, 공용 파일에 값이 들어가면 다음 동기화에서 납품 패키지에 그대로
> 실려 나간다 — 고객사에서 아무도 선택하지 않은 채 되돌릴 수 없는 삭제가 시작된다.
> 환경별 파일(`gate-service-dev.yml` 등)을 만들어 거기에만 넣고, 넣기 전에 On-prem 세션에
> 알린다. (onprem `cf4156a` 의 `build_package.sh` 가 `config/spring` 에 `retention-days:` 가
> 있으면 빌드를 중단한다 — 납품처와 기간을 합의한 경우에만 `--allow-purge-keys` 로 통과시킨다.)

켜기 전에 정해야 할 것은 하나다 — **삭제 후 며칠 뒤에 지울 것인가.** 그 값이 복구 창의
길이다.

> 인증·특징점 **이력** 의 보존 기간은 별개다 — [history-retention.md](history-retention.md) 참고.

## 무엇을 지우고 무엇을 남기는가

| 대상 | 처리 |
|---|---|
| `biometric_feature` 행 | **물리 삭제** (소프트 삭제된 행 포함) |
| 특징점의 원본 이미지 파일 | 삭제 |
| face-service · palm-service 쪽 저장분 | 각 서비스의 삭제 API 호출 |
| `match_history` · `feature_history` | **남긴다** (감사 기록) |

이력을 남기는 이유는 그것이 감사 기록이고, 보존 기간이 UG-282 와 같은 법적 판단을 필요로
하기 때문이다.

**행은 남지만 그 행이 가리키는 이미지는 사라진다.** 등록 사건의 `feature_history` 행은
`biometric_feature` 와 같은 경로 문자열을 갖는다 (등록 시 하나의 경로를 양쪽에 넣는다).
개인정보를 지우는 것이 이 기능의 목적이므로 그 편이 맞고, 외래 키가 없어 행이 깨지지도
않는다. 다만 "이력은 남는다" 를 "이미지도 남는다" 로 읽으면 안 된다.

소프트 삭제된 특징점도 대상이다. 오히려 더 오래 방치된 데이터다.

## 언제 도는가

매일 20:00 UTC (05:00 KST). `auth-service` 의 리프레시 토큰 퍼지 잡(19:00 UTC)과 한 시간
띄워 새벽 작업이 겹치지 않게 했다.

실행당 프로젝트 50개가 상한이다. 누적분이 많은 첫 실행에서 수천 개 프로젝트의 하위 서비스
삭제를 한 번에 쏘면 그쪽이 먼저 넘어간다. 남은 것은 다음 밤에 처리한다.

## 실패하면 어떻게 되나

**하위 서비스(face·palm) 삭제가 먼저다.** 성공한 뒤에야 gate 의 행을 지운다. 순서를 뒤집으면
gate 에는 없고 하위에는 남은 고아가 생기고, 그것은 어느 경로로도 다시 찾을 수 없다.

| 실패 지점 | 동작 |
|---|---|
| 하위 서비스가 "없다" 고 응답 | **성공으로 본다.** 우리가 지우려던 상태이므로 그대로 정리를 끝낸다 |
| 그 밖의 하위 서비스 삭제 실패 | 그 특징점은 그대로 두고 다음 특징점으로. 다음 실행에서 재시도 |
| MinIO 이미지 삭제 | 경고만 남기고 특징점은 지운다. 고아 파일은 접근 경로가 없다 |
| 프로젝트 하나가 통째로 실패 | 나머지 프로젝트는 계속 처리. 다음 실행에서 재시도 |

한 건 때문에 전체를 멈추면 하위 서비스 한 대의 장애가 정리를 영구히 세운다 — 그 사이
지워졌어야 할 개인정보가 계속 남는다.

## 이미 삭제된 특징점은 하위 서비스를 부르지 않는다

제품 API 의 특징점 삭제는 하위 서비스 삭제가 **성공한 뒤에야** `is_deleted` 를 찍는다. 즉
소프트 삭제된 특징점은 하위에 이미 없다. 그런데도 부르면 match 가 `INVALID_FACE_ID`
(MATCH-004, 400) 를 돌려주고, 그것을 실패로 세면 **제품 API 로 삭제된 특징점은 영원히
정리되지 않는다.** 그래서 그 경우 하위 호출을 건너뛴다.

부분 실패 뒤 재시도(하위 삭제는 성공했는데 커밋이 실패한 경우)를 위해 "없다" 응답도 성공으로
본다. face 경로의 코드는 확인했다. **palm 은 미확인이다** — 벤더 모듈의 응답 코드를 확인하지
못했고, palm 은 위의 건너뛰기에만 기댄다. 재시도에서 막히면 로그의 사유를 보고 목록에 추가할
것 (`ProjectDataPurgeService.없음을_뜻하는_사유`).

## 정리가 끝난 프로젝트

대상 조회는 **지울 특징점이 남은** 프로젝트만 고른다. 정리가 끝나면 목록에서 빠진다.

이 조건이 종료 조건이다. 없으면 정리된 프로젝트가 계속 대상으로 남고, 오래된 것부터 고르므로
실행당 상한 50개를 영구히 차지해 그 뒤의 프로젝트가 영원히 정리되지 않는다.

프로젝트 행 자체는 지우지 않는다. 소프트 삭제된 프로젝트를 남기는 것이 UG-288 의 설계이고,
이 기능이 지우는 것은 생체 데이터다.

## 제외되는 것

`deleted_at` 이 `NULL` 인 프로젝트는 대상이 아니다. V32 이전에 삭제된 행은 삭제 시각을 알 수
없어 유예를 잴 수 없다. 임의로 채워 지우는 것보다 남기는 쪽이 안전하다.

그런 행이 실제로 있는지는 배포 뒤 확인할 수 있다.

```sql
SELECT count(*) FROM projects WHERE is_deleted = true AND deleted_at IS NULL;
```

0 이 아니라면 그 프로젝트들은 이 잡으로 정리되지 않는다. 수동 처리가 필요하면 별도로 정한다.

## 다중 인스턴스

gate 는 환경당 단일 인스턴스 전제다. 여러 대로 가면 분산 락이 필요하다 — 두 대가 같은
프로젝트를 동시에 정리하면 하위 서비스 삭제가 중복 호출된다.

**온프레미스는 단일 인스턴스임을 확인했다** (2026-09-22, onprem 저장소 확인). compose 에
`replicas` 나 `deploy` 블록이 없고 수평 확장 구성을 제공하지 않는다. 다중 인스턴스 구성이
생기면 그쪽에서 먼저 알리기로 했다.

중복 호출이 나더라도 지금은 파괴적이지 않다. 두 번째 호출은 "없다" 응답을 받고, 그것을
성공으로 보므로(위 참고) 양쪽 다 정리를 끝낸다. 다만 그 판정이 face 경로에서만 확인됐으므로
분산 락 없이 여러 대를 띄우는 것은 여전히 권하지 않는다.

## 관련

- UG-288 — 프로젝트 소프트 삭제와 API 키 비활성화
- UG-282 — 매칭 이력 보존 정책 (같은 법적 판단이 필요하다)
- UG-250 — `auth-service` 의 리프레시 토큰 퍼지 잡 (이 잡의 구조가 그것을 따랐다)
